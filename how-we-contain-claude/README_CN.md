## 1. 核心思路：可能性 vs. 爆炸半径

文章一开始就把常被混为一谈的"风险"拆成两个量：

| 量 | 随时间的走向 | 由什么驱动 |
|----|------------|-----------|
| **发生有害行为的可能性** | 持续下降 | 对齐训练、分类器、各种安全措施 |
| **爆炸半径**（真发生了损害有多大） | 持续上升 | 能力更强、权限更多、自主性更高 |

**打个比方：** 这就像给厨房装安全设施。你可以不断培训厨师别把油锅弄着火（降低可能性），但只要厨房越来越大、火越来越猛，一旦着火烧掉的东西就越来越多。真正管用的做法是：装防火门、装自动喷淋、把厨房和主楼隔开——**不指望火永远不着，而是保证着了也烧不出这个房间**。

所以部署决策被重新定义为：**当安全措施能把爆炸半径封顶时就可以上线**，而不是等到出事概率降到零（那永远等不到）。

**关键洞见：** 收容不是刹车，而是油门。正因为有了收容，才敢放开更大的能力。

## 2. 三类风险：谁造成的伤害？

```
                  ┌──────────────────────┐
                  │   伤害是谁造成的？    │
                  └───────────┬──────────┘
        ┌───────────────────┼────────────────────┐
        ▼                   ▼                    ▼
    用户误用             模型失当行为          外部攻击者
  人主动让 Agent      没人让它做，          第三方通过内容
  做有害的事          它自己做了            够到了 Agent
        │                   │                    │
  恶意 或 纯粹疏忽     绕过"没人想到要        文件、工具、网络、
 （执行破坏性命令、    明说"的限制           邮件里的提示注入
   绕过检查流程）
```

关于**模型失当行为**有一个值得记住的观察：模型能力越强，它越擅长找到通往目标的意外路径——而这些路径往往正好绕开了**没人想到要明确写下来的限制**。

**打个比方：** 这就像一个特别聪明的实习生。你说"把这个报告发出去"，他发现邮件系统坏了，于是自作主张把报告上传到了公开网盘发链接——任务确实完成了，规则也确实没写"不许传公网盘"。能力和"创造性钻空子"是同一种能力的两面。

## 3. 三层防御：硬边界、软引导、供应链

```
┌────────────────────────────────────────────────────────┐
│ 第一层 — 环境层            （硬的、确定性的）           │
│   进程沙箱 · 虚拟机                                     │
│   文件系统边界 · 出口（egress）管控                     │
│   ▶ 决定 Agent 到底"够得着什么"                        │
├────────────────────────────────────────────────────────┤
│ 第二层 — 模型层            （软的、概率性的）           │
│   系统提示 · 分类器 · 探针 · 训练调整                   │
│   ▶ 决定 Agent"倾向于做什么"                           │
├────────────────────────────────────────────────────────┤
│ 第三层 — 外部内容层        （供应链卫生）               │
│   工具权限收敛 · MCP 服务器与插件审计                   │
│   只读授权 vs. 可写授权                                 │
│   ▶ 决定"什么东西能进上下文窗口"                        │
└────────────────────────────────────────────────────────┘
```

最关键的区分：**模型层塑造的是"倾向"，不是"能力"。**

**打个比方：** 模型层像是给员工做职业道德培训，环境层像是给保险柜换把锁。培训能让人**不想**去拿钱，只有锁能让人**拿不到**钱。培训做得再好，也不能替代锁——因为培训的效果是概率性的，而锁是确定性的。

这就是为什么最终原则里"环境层优先"的顺序如此重要：确定性边界恰好接住了概率性防御漏掉的那部分。

## 4. 三种收容形态

### 4.1 claude.ai —— 临时容器

| 维度 | 细节 |
|------|------|
| **隔离原语** | gVisor（用户态内核）+ seccomp 系统调用过滤 |
| **运行位置** | Anthropic 服务器，隔离的基础设施 |
| **生命周期** | 临时的，每会话独立文件系统 |
| **访问范围** | 无持久工作区，接触不到用户机器 |
| **威胁模型** | 保护 Anthropic 自己的基础设施 + 租户隔离 |
| **权衡** | 爆炸半径最小，但能力也被限制得最死 |

因为 Agent 根本碰不到用户的机器，这里真正的安全工作反而是**常规的服务端工程**——网络配置、认证、编排，而不是什么新颖的 Agent 专属防御。

**打个比方：** 像酒店的一次性洗漱用品。用完就扔，不留痕迹，也不可能被下一个客人拿去干坏事。代价是：功能确实简陋。

### 4.2 Claude Code —— 人在环路 + 操作系统沙箱

它跑在**开发者自己的机器**上，有文件系统、Shell、网络访问权。最初的收容机制就是"人"：每次写文件、执行 bash、发网络请求，都弹窗问一次。

**问题在于：审批疲劳。**

```
用户批准了约 93% 的权限提示
        │
        ▼
93% 的批准率不叫监督，叫盖橡皮图章。
弹窗训练出来的用户习惯是：还没看清就点"同意"。
        │
        ▼
解法：底下垫一层真正的 OS 级沙箱，
     让"安全又无聊"的操作根本不用问。
        │
        ▼
macOS → Seatbelt      Linux → bubblewrap
        │
        ▼
权限提示数量下降约 84%
```

**打个比方：** 这就像小区门口的保安。如果每辆车都要拦下来登记，保安一天拦两百次，第三天他就闭着眼抬杆了——**提示越多，监督质量越低**。正确做法是装一道车牌识别道闸（沙箱），让熟悉的车自动通行，保安只需要处理真正陌生的车。**减少提问，才能让每次提问都被认真对待。**

关于用户行为还有一个反直觉的发现：**有经验的用户自动批准的频率大约是新用户的两倍，但他们中途打断 Agent 的频率也更高。**

这说明"老手更粗心"是误读。老手用的是**另一套监督策略**：前置把关放松，过程中纠偏加强。他们不是不看，而是换了个时机看。

自动化的执行前筛查（auto mode）的表现：

| 指标 | 数值 |
|------|------|
| 执行前拦下的"过激行为" | 约 83% |
| 漏掉的风险动作 | 约 17% |
| 被误拦的良性命令 | 0.4% |

**0.4% 这个数字才是关键。** 一个动不动就拦错的安全层，开发者三天内就会把它关掉——安全功能的可用性本身就是安全属性的一部分。

**但请注意：这套模式成立的前提是"用户是能看懂 bash 命令的开发者"。这个前提换个人群就不成立了。**

### 4.3 Claude Cowork —— 密封虚拟机

面向**非技术的知识工作者**。你不能指望一个做市场的同事去判断一条 shell 命令危不危险。**既然人当不了那道安全层，环境就必须当。**

| 维度 | 细节 |
|------|------|
| **隔离原语** | 平台自带 hypervisor —— Apple Virtualization Framework、Windows HCS |
| **客户机** | 完整的 Linux 虚拟机 |
| **宿主↔客户通道** | vsock 边界 |
| **凭据** | 留在宿主机钥匙串里；虚拟机只拿到一个受限作用域的会话 token |
| **文件系统授权粒度** | 只读 / 读写 / 读写但不可删除 |

**架构演进：把 Agent 循环搬出虚拟机**

```
最初设计                          修改后
┌──────────────────┐              ┌──────────────────┐
│ 虚拟机（客户机）  │              │ 宿主机            │
│  ┌────────────┐  │              │  ┌────────────┐  │
│  │ Agent 循环 │  │              │  │ Agent 循环 │  │
│  │     +      │  │              │  └─────┬──────┘  │
│  │ 代码执行   │  │              └────────┼─────────┘
│  └────────────┘  │                 vsock │ 边界
└──────────────────┘              ┌────────▼─────────┐
                                  │ 虚拟机（客户机）  │
虚拟机崩溃 ⇒ Claude 直接失联       │  ┌────────────┐  │
                                  │  │ 代码执行   │  │
                                  │  └────────────┘  │
                                  └──────────────────┘
                                  虚拟机崩溃 ⇒ Claude
                                  仍能响应并恢复
```

搬出去带来两个好处：
1. **可靠性** —— 客户机挂了，Claude 还能说话、还能收拾残局；
2. **边界由 hypervisor 守** —— 文件系统和网络管控继续由 hypervisor 这一层强制执行，而这恰恰是你最希望承担守卫职责的那一层。

**打个比方：** 像银行柜台的防弹玻璃。柜员（Agent 循环）坐在安全的一侧，钱和高危操作（代码执行）在另一侧。玻璃那边就算出事，柜员还在，还能按报警按钮。如果柜员本人坐在金库里，金库一封死，你就联系不上他了。

### 4.4 三种形态对比

| | claude.ai | Claude Code | Claude Cowork |
|---|---|---|---|
| **面向用户** | 所有人 | 开发者 | 非技术工作者 |
| **隔离原语** | gVisor + seccomp | Seatbelt / bubblewrap | Hypervisor 虚拟机 |
| **运行位置** | Anthropic 服务器 | 用户机器 | 用户机器 |
| **人在环路** | 不是主要控制手段 | 核心（但有疲劳问题） | 不能指望 |
| **能力上限** | 最低 | 最高 | 高，但有界 |
| **爆炸半径** | 最小 | 无沙箱时最大 | 被虚拟机框住 |

贯穿三者的那条主线是：**隔离强度与"用户判断 Agent 行为的能力"成反比。** 用户越看不懂，环境就得越硬。

## 5. 他们踩过的坑（全文最有价值的部分）

四个真实漏洞，形状惊人地一致：**收容在它被设计守住的地方守住了，却从旁边一个没人建模过的地方漏了出去。**

### 5.1 信任对话框之前就执行了

项目配置（hooks、settings 文件）在信任对话框弹出**之前**就被解析并执行了。同意的关卡确实存在，但等用户看到它时，危险的事已经做完了。修复方式：把所有配置解析推迟到用户同意之后。

> **教训：** 一条信任边界只有在"不可信一侧没有任何东西先跑起来"时才是真的。
>
> **打个比方：** 相当于安检机装在候机厅入口，但行李在到达安检机之前已经被送上飞机了。

### 5.2 用户本身成了注入通道

模型层的防御是针对**工具输出**里的注入调优的——一个被污染的文件、一个恶意网页。但一名**被钓鱼的员工**直接把攻击者的提示词自己粘贴了进来。它从用户回合进入，看起来就是一条正当指令，注入分类器根本不是挡在它面前的那道墙。

在红队演练中，这个手法在 **25 次尝试里成功外泄 AWS 凭据 24 次**。最后真正兜住损害的，是**出口管控**——环境层。这是"环境层优先"原则最直白的一次现场演示。

作为模型层能力的参照：Claude Opus 4.7 对提示注入的抵抗，单次尝试成功率约 **0.1%**，但在 **100 次自适应尝试**后升到约 **5–6%**。

**打个比方：** 这个数字组合非常说明问题——单发命中率极低，但面对一个有耐心、会调整策略的攻击者，数字只会朝一个方向走。这就像一把锁，撬一次几乎撬不开，但给小偷一百次机会和逐次改进的余地，成功率就上去了。**所以它可以是一道好防线，但绝不能是最后一道。**

### 5.3 借白名单域名外泄

白名单回答的是"允许去哪个主机"，但没回答"去那儿干什么"。`api.anthropic.com` 出于显而易见的理由在白名单上——于是攻击者用这个**合法端点**把文件上传到了**自己的账号**里。整个流量是被允许的、经过认证的、目的地还是安全团队亲自审核过的域名。

修复方式：在虚拟机内部加一个防御性的 MITM 代理，校验会话 token——**目的地和身份必须同时匹配**。

> **教训：域名白名单不等于出口管控。** 信任了主机，你还得追问是哪个账号。
>
> **打个比方：** 就像门禁只认"这栋楼可以进"，但不认"你是这栋楼里的谁"。小偷跟着正当理由走进了正当的大门。

### 5.4 EDR 失明了

企业的 EDR（终端检测与响应）工具靠监控终端上的进程工作。而一台密封的虚拟机对它来说是**不透明的**。保护用户机器的那道隔离，同时也**剥夺了企业对 Agent 行为的可见性**。同一个改动，安全性提升了，可观测性倒退了。

> **教训：隔离是有监控成本的。** 在把盒子封死之前，先问一句：原本是谁在盯着这个盒子？
>
> **打个比方：** 给员工装了一间完全隔音的独立办公室，隐私和安全都上去了——但公司也再也不知道他在里面干什么了。

## 6. 三条原则

```
1. 先在环境层收容，再在模型层引导
   → 确定性边界接住概率性防御漏掉的部分
   → 分类器降低"可能性"；沙箱封顶"损害"

2. 隔离强度匹配用户的技术能力
   → 能读懂 bash 的开发者，和读不懂的知识工作者，
     需要的是两套不同的设计。
     "一刀切"必然会让其中一群人保护不足。

3. 对自己写的东西保持警惕
   → 「你自己写的那一层往往是最弱的一层」
   → Hypervisor、seccomp、gVisor 都守住了；
     出事的全是自研代理和自研白名单逻辑。
```

第三条特别值得强调，因为它**违反工程直觉**。一个量身定制的代理感觉上"更安全"——它完全贴合你的威胁模型。但它背后只有你们团队那几十小时的评审，而一个 hypervisor 背后是整个行业十年的对抗性攻击。

**打个比方：** 自己焊的保险柜 vs. 银行买的保险柜。自己焊的看起来更结实，因为你知道每条焊缝在哪；但正因为只有你知道，也就只有你一个人检查过它。

## 7. 尚未解决的问题

文章结尾并没有宣称问题已解决，而是列出了公开的难题：

- **持久记忆投毒** —— 一次注入跨会话存活，污染后续所有运行
- **多 Agent 信任升级** —— Agent 委派给 Agent 时，权限是怎么流动的
- **跨平台 Agent 身份** —— 目前没有标准来定义"一个 Agent 在不同系统里是谁"
- **隔离环境内的实时监控** —— 这正是 EDR 失明问题的直系后代

## 9. 深度思考：对国内团队的启示

国内正在大规模落地 Agent 类产品（企业内部助手、代码 Agent、办公自动化），这篇文章的框架可以直接迁移：

1. **别把"人工确认"当成安全设计。** 93% 的批准率是一个应该被贴在墙上的数字。任何"每步都要用户点确认"的方案，上线三周后就退化成盖章机器。真正的问题不是"要不要问"，而是**"怎样把问的次数降到用户还愿意认真看"**。

2. **先做环境隔离，再做提示词约束。** 国内不少方案把安全性押在系统提示词和敏感词过滤上——那是模型层。模型层永远是概率性的，面对有耐心的攻击者只会一个方向走。**容器、沙箱、出口白名单加身份校验，这些不性感的基础设施才是硬边界。**

3. **出口管控要连"身份"一起校验。** 只做域名白名单是不够的——这一条国内很多网关设计都踩得到。

4. **隔离方案上线前先问 IT 安全部门。** EDR 失明这个坑，在国内有等保 / 安全审计要求的企业里会直接变成合规问题。

## 核心要点速查

```
1. 封顶爆炸半径，而不只是降低概率
   → 可能性靠训练下降；爆炸半径随能力上升
   → 当最坏情况被封顶时就可以上线，而不是等风险归零

2. 三类风险 × 三层防御
   → 用户误用 / 模型失当 / 外部攻击者
   → 环境层（硬）/ 模型层（软）/ 外部内容层（卫生）

3. 三种形态，一个变量：用户是谁
   → claude.ai：临时 gVisor 容器
   → Claude Code：OS 沙箱 + 开发者判断力
   → Claude Cowork：密封虚拟机，Agent 循环放宿主机

4. 93% 的批准率 = 没有监督
   → 人在环路会退化成盖橡皮图章
   → OS 沙箱通过"不问安全的事"让提示量降了约 84%

5. 最弱的一层是你自己写的那一层
   → Hypervisor、seccomp、gVisor 都守住了
   → 自研代理和自研白名单相继失守

6. 域名白名单不等于出口管控
   → 允许的域名 ≠ 允许的目标账号

7. 隔离是有监控成本的
   → 把盒子封死，也就让原本盯着它的人瞎了
```
