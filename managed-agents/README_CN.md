## 整体思维导图

```
扩展托管 Agent（Managed Agents）
├── 核心问题
│   └── harness 把"模型做不到什么"的假设固化进代码，模型一升级假设就过期
│       └── 实例：Sonnet 4.5 "上下文焦虑" → 加入上下文重置
│              Opus 4.5 该行为消失 → 重置逻辑变成死重
├── 操作系统类比
│   ├── 把硬件虚拟化成抽象（process、file）
│   ├── 通用到足以服务"尚未被设想出来的程序"
│   └── read() 不关心是 1970 年代磁盘组还是现代 SSD
├── 三个被虚拟化的组件
│   ├── session —— append-only 事件日志
│   ├── harness —— 调用 Claude、路由工具调用的循环
│   └── sandbox —— 执行环境
├── 不要养宠物
│   ├── 全部塞进一个容器 = 宠物 vs 牲畜问题
│   ├── 容器挂了 → 整个 session 丢失
│   ├── 无法调试（唯一窗口只有 WebSocket 事件流）
│   └── 接入客户 VPC 需要网络对等互联（peering）
├── 解耦大脑与双手
│   ├── harness 搬出容器
│   ├── execute(name, input) -> string
│   ├── provision({resources})
│   ├── 容器变成"牲畜"；故障 = 普通工具调用错误
│   └── harness 自己也变成牲畜：wake / getSession / emitEvent
├── 安全边界
│   ├── 耦合时：凭证和不可信代码在同一容器
│   ├── 模式 A：凭证与资源绑定（git remote）
│   └── 模式 B：凭证放在沙箱外的 vault（MCP OAuth 代理）
├── session ≠ 上下文窗口
│   ├── 压缩 / memory 工具 / 裁剪 都是不可逆决策
│   ├── session 活在上下文窗口之外，持久化存储
│   ├── getEvents() → 位置切片（续读 / 回退 / 重读）
│   └── harness 可以任意变换取回的事件
└── 多个大脑，多双手
    ├── 不再需要 VPC peering；容器按需provision
    ├── p50 TTFT ↓ 约 60%，p95 TTFT ↓ 超过 90%
    ├── 任意"手"：容器、手机、宝可梦模拟器
    └── 大脑之间可以互相传递"手"
```

## 1. 核心问题：harness 里的假设会过期

harness（脚手架）就是那个"调用 Claude、拿到工具调用请求、执行、再喂回去"的循环。工程师在写它的时候，不可避免地会把**"模型现在做不到什么"**的判断写进代码——而这些判断是有保质期的。

**文中给出的标志性例子：**

| 模型 | 行为 | harness 的应对 | 结果 |
|------|------|---------------|------|
| Sonnet 4.5 | "上下文焦虑"（context anxiety），上下文变满时表现下降 | harness 主动做上下文重置 | 当时是必要的补丁 |
| Opus 4.5 | 该行为消失了 | 重置逻辑还在照常触发 | **变成死重（dead weight）** |

> **通俗比喻：** 这就像你给一个近视的同事把所有文件都打印成超大字号。后来他做了近视手术，视力恢复了，可你的打印脚本还在跑——现在每份文件都变成一摞纸，反而碍事。**补丁活得比问题还久**，这才是麻烦所在。

**核心洞见：** 你没法在"当前模型的缺点"之上建一个能长期存在的 Agent 平台。你需要的是**能熬过模型换代的抽象**。

## 2. 操作系统类比

文章的核心思想工具：操作系统几十年前就解决过一模一样的问题。

```
硬件                →  虚拟化后的抽象  →  性质
──────────────────────────────────────────────────
磁盘组（1970 年代） →  file           →  read() 照常工作
SSD（现代）         →  file           →  read() 照常工作
CPU / 内存          →  process        →  调度器照常工作
```

操作系统把硬件虚拟化成 **process**、**file** 这样的抽象，而且这些抽象要通用到能服务**"尚未被设想出来的程序"**。`read()` 完全不关心底下的字节来自 1970 年代的磁盘组还是现代 SSD——**抽象活得比它下面的每一代实现都久**。

> **通俗比喻：** 想想"插座"这个抽象。1950 年造的插座，今天照样能给手机充电。插座设计者不知道会有手机，但他定义的是**接口**（两个孔、220V），不是**实现**（当年只有电灯泡）。Managed Agents 想给 Agent 找的就是这种"插座"。

Managed Agents 用同样的招式虚拟化三个组件：

| 组件 | 定义 | 概念上对应的 OS 抽象 |
|------|------|---------------------|
| **session** | Agent 活动的 append-only（只追加）事件日志 | 持久化的文件 / 日志 |
| **harness** | 调用 Claude、路由工具调用的循环 | 进程（process） |
| **sandbox** | 执行环境 | 被虚拟化的机器 |

一句话总结原则：**对接口固执己见，对实现保持开放。**

## 3. "不要养宠物"

最早的架构把所有东西——harness、sandbox、session 状态——**全塞进一个容器**。这就掉进了运维界经典的**「宠物 vs 牲畜」（pets vs. cattle）**陷阱。

> **通俗比喻：**
> - **宠物**：你给它起名字，生病了要带去看医生、心疼、想尽办法救活。它是不可替代的。
> - **牲畜**：编号管理，出问题就换一头，流程完全不受影响。
>
> 服务器该当牲畜养，可当时那个容器活成了宠物。

### 具体出了什么问题

```
┌─────────────────────────────────────────┐
│              一个容器                    │
│  ┌──────────┐  ┌──────────┐            │
│  │ harness  │  │ sandbox  │            │
│  └──────────┘  └──────────┘            │
│  ┌──────────┐  ┌──────────┐            │
│  │ session  │  │ 用户数据  │            │
│  │  状态    │  │ + 凭证    │            │
│  └──────────┘  └──────────┘            │
└─────────────────────────────────────────┘
        │
        └── WebSocket 事件流（唯一能往里看的窗口）
```

| 故障场景 | 后果 |
|---------|------|
| **容器挂掉** | session 跟着一起没了，工作成果不可恢复 |
| **容器卡死** | 无法调试：唯一能往里看的窗口只有 WebSocket 事件流 |
| **用户数据同处一室** | 连这个窗口都不能随便看——用户数据就在同一个容器里 |
| **接入客户 VPC** | 必须做网络对等互联（peering），因为 harness 假定了自己和资源在同一个地方 |

更糟的是：这只"宠物"手里**同时握着凭证和不可信的生成代码**。

## 4. 解耦大脑与双手

解法很干脆：**让 harness 搬出容器。**

### 4.1 沙箱降级成一个"工具"

harness 不再*住在*执行环境里，而是像调用**任何其他工具**一样调用它：

```
execute(name, input) -> string     # 执行
provision({resources})             # 申请资源
```

一只"手"的接口就这么点东西。带来的变化：

- 容器变成了**牲畜**——匿名、可替换、用完即弃。
- 容器故障不再是基础设施事故，而是**以普通"工具调用错误"的形式返回**——而模型本来就很擅长处理工具报错并重试。
- 资源通过 `provision({resources})` 显式申请，不再被焊死在固定镜像里。

### 4.2 harness 自己也变成牲畜

一旦 session 状态存在 harness 之外，harness 本身也就可以随时丢弃了：

```
wake(sessionId)            → 在已有 session 上重启一个 harness
getSession(id)             → 取回 session 历史
emitEvent(id, event)       → 往日志追加新的活动
```

harness 挂了，就换一个新的：调 `wake(sessionId)`，用 `getSession(id)` 读历史，然后继续用 `emitEvent(id, event)` 追加。**Agent 的任何进度从来就没存在 harness 的内存里过。**

```
改造前                          改造后
──────                          ─────
┌───────────────┐               ┌─────────┐   execute()   ┌─────────┐
│ harness       │               │ harness │ ────────────▶ │ sandbox │
│ + sandbox     │  ← 宠物        │ (大脑)  │ ◀──────────── │ (双手)  │
│ + session     │               └────┬────┘   结果/报错   └─────────┘
└───────────────┘                    │
   ↓ 一挂全丢            wake / getSession / emitEvent
                                     │
                                ┌────▼────┐
                                │ session │  ← 持久化，独立于两者之外
                                └─────────┘
```

> **通俗比喻：** 以前是"厨师住在厨房里，菜谱也写在厨房墙上"——厨房一失火，厨师、菜谱、菜全没了。现在是：菜谱存在云端（session），厨师站在厨房外面遥控（harness），厨房只是个可替换的操作间（sandbox）。厨房烧了？换一间，照着云端菜谱接着做。

## 5. 安全边界

耦合架构有一个非常具体、非常严重的漏洞：**不可信的生成代码和凭证跑在同一个容器里。**

```
耦合架构（不安全）
  提示注入 → 读取环境变量 → 拿到 token
           → 启动不受限制的 session
```

一次提示注入（prompt injection）攻击就能读环境变量、拿到凭证，并启动不受限制的 session。解耦把这个问题从"需要时刻警惕"变成了**结构性保证：token 从沙箱里根本够不着。**

具体有两种模式：

### 模式 A —— 凭证与资源绑定

凭证在*资源初始化时被消耗掉*，直接接进资源里，从不交到 Agent 手上。

> Git access token 在沙箱初始化时把仓库 clone 下来，并被接进本地的 git remote 配置。之后 `push` / `pull` 照常工作，而 **Agent 从头到尾没碰过这个 token。**

### 模式 B —— 凭证放在沙箱外的保险库（vault）

凭证存在外面，由一个 Agent 够不着的组件按需兑换。

> MCP 的 OAuth token 存在 vault 里。Claude 通过一个**专用代理（proxy）**调用 MCP，由代理拿 session token 去兑换真正的凭证。**harness 自始至终看不到凭证。**

| 模式 | 凭证存放位置 | Agent 能看到什么 | 例子 |
|------|-------------|-----------------|------|
| A：与资源绑定 | 初始化时写进资源配置 | 什么都看不到 | git remote |
| B：vault + 代理 | 外部 vault | 只有 session token | MCP OAuth |

> **通俗比喻：**
> - **模式 A** 像是酒店房卡：前台用你的身份证开了卡，你拿着卡能开门，但卡上没有你的身份证信息。房卡丢了，损失可控。
> - **模式 B** 像是代驾：你把车钥匙交给管家（vault），叫车时管家派司机去开，你手上只有一张叫车凭条。

**原则：不要指望 Agent 小心保管密钥，而要让密钥从一开始就不在它手边。**

## 6. session 不是 Claude 的上下文窗口

这是全文概念上最吃重的一个区分。

长周期任务必然超出上下文窗口，于是 harness 得对上下文动手——而**每一次动手都是不可逆的决策**：

| 手段 | 丢掉了什么 | 风险在哪 |
|------|-----------|---------|
| 压缩（compaction） | 细节，被摘要替代 | 摘要没法"反摘要"回去 |
| memory 工具 | 没被写下来的一切 | 写什么本身就是一次猜测 |
| 上下文裁剪 | 较早的轮次 | 很难知道未来某一轮会需要哪些 token |

问题不在于这些手段本身不好。问题在于**它们有损且不可逆**，而你必须在还不知道什么会重要的时候就做决定。

> **通俗比喻：** 这就像整理房间时扔东西。压缩 = 把一箱资料浓缩成一页笔记；裁剪 = 直接扔掉旧的。等三个月后你需要当初那份合同附件时，才发现它早被"整理"掉了——**而且没有回收站**。

### 解法：session 是活在上下文窗口之外的"上下文对象"

```
        ┌──────────────── SESSION（持久化存储） ──────────────────┐
        │  e0  e1  e2  e3  e4  e5  e6  e7  e8  e9  e10 ...        │
        └──────────────────────────────────────────────────────────┘
             │            │                    │
        getEvents()  getEvents()          getEvents()
           回退         重读                 续读
             │            │                    │
             ▼            ▼                    ▼
        ┌──────────────────────────────────────────────┐
        │ harness：变换 → 送进 Claude 的上下文窗口       │
        └──────────────────────────────────────────────┘
```

`getEvents()` 支持对日志做**位置切片（positional slices）**，于是有了三种动作：

- **续读（resume）** —— 从上次读到的地方接着往下
- **回退（rewind）** —— 退回到某个时刻之前
- **重读（reread）** —— 做某个动作之前，重新看一遍日志

而且 harness 可以在事件送进 Claude 之前**任意变换**它们——为了提高 prompt cache 命中率，或者执行任何它想用的上下文工程策略。

### 关注点分离

| 层 | 负责保证 | 可以随便折腾 |
|----|---------|-------------|
| **session** | 持久性（durability）+ 可审查性（interrogability） | —— |
| **harness** | —— | 任意的上下文管理策略 |

session 只承诺"数据还在、且随时能查"。至于**给模型看什么**，完全是 harness 的自由——而且可以每次模型更新都改一遍，永远不会因此丢数据。

> **这才是第 1 节问题的真正答案**：把易变的、模型相关的逻辑（上下文策略）关进 harness 这个可丢弃的层，把不可变的资产（数据）放进 session。模型换代时，你扔掉的只是 harness。

## 7. 多个大脑，多双手

解耦带来的收益远不止可靠性。

### 7.1 性能

因为 harness 不再和 sandbox 住一起，它**不再需要 VPC peering**；容器也可以**只在真正需要时才 provision**，而不是每个 session 一开始就先起一个。

| 指标 | 改善幅度 |
|------|---------|
| **p50 TTFT** | 下降约 **60%** |
| **p95 TTFT** | 下降**超过 90%** |

**TTFT**（time-to-first-token）= 从接下任务到吐出第一个响应 token 的时间，也是**用户感受最直接的延迟**。

> p95 那个数字才是真正惊人的：**最糟糕的那批等待——也就是让人觉得"这产品是不是坏了"的那些时刻——基本上消失了。** 平均值好看不难，尾延迟塌下来才是架构真的对了。

### 7.2 多双手

因为一只"手"无非就是 `execute(name, input) -> string`，harness **根本不知道、也不关心线的另一头是什么**：

```
                  ┌─────────┐
        ┌─────────│ harness │─────────┐
        │         └────┬────┘         │
   execute()      execute()      execute()
        │              │              │
        ▼              ▼              ▼
  ┌──────────┐   ┌─────────┐   ┌──────────────┐
  │  容器    │   │  手机   │   │  宝可梦模拟器 │
  └──────────┘   └─────────┘   └──────────────┘
```

文章点名的就是这三个：一个容器、一部手机、一个宝可梦模拟器。**接口相同，实现任意**——第 2 节那个操作系统类比在这里字面意义地兑现了。

### 7.3 多个大脑

既然大脑是无状态的、手是可寻址的工具，那么**大脑之间可以互相传递"手"**。多 Agent 拓扑从一个基础设施问题，变成了一个组合（composition）问题。

---

## 8. 结论：一个"元 harness"

Managed Agents 给自己的定位是**元 harness（meta-harness）**：**对接口固执己见，对实现保持开放。**

它强制规定你**怎么操作状态**（`getSession`、`emitEvent`、`getEvents`）和**怎么申请算力**（`execute`、`provision`），但对你**在上面写什么循环**完全不发表意见。这正是操作系统当年的交易条件——**把抽象钉死，好让建在上面的东西自由变化**。

背后的赌注是：模型行为一定会继续变，所以最终能活下来的那一层，恰恰是那个从来没有声称自己知道模型需要什么的层。

## 10. 深度思考

### 对国内 Agent 平台建设的启示

国内做 Agent 平台（如各家云厂商的 Agent 服务、Coze/扣子这类编排平台）时，最容易犯的就是"把执行沙箱和调度逻辑焊在一起"。本文给出的三条可直接借鉴：

1. **session 必须独立持久化** —— 不要让任务进度只存在于某个进程或容器的内存里。
2. **凭证走绑定或代理，绝不进沙箱** —— 尤其在开放插件生态下，提示注入是必然会发生的，而不是可能会发生的。
3. **按需 provision 沙箱** —— 尾延迟（p95）的改善往往比平均延迟更能决定产品口碑。

### 更深层的启示

这篇文章真正的主题其实不是 Agent，而是**如何在一个快速变化的底层之上构建稳定的系统**。答案是老答案：**分清什么是接口、什么是实现，然后只对接口做承诺。**

当你发现自己在代码里写下"因为模型现在还不能……"时，就该警觉：这行注释正在给你的系统设定保质期。合适的做法不是不写这行代码，而是**把它关进一个你随时可以整体丢掉的层里**。

## 核心要点速查

```
1. harness 里的假设会过期
   → Sonnet 4.5 的上下文重置，到 Opus 4.5 就成了死重

2. 对接口固执，对实现开放
   → read() 活得比磁盘组久；execute() 也该活得比容器久

3. 不要养宠物
   → sandbox 和 harness 都该是牲畜
   → 容器故障 = 一次工具调用报错，而不是一场事故

4. 密钥要够不着，而不是"小心保管"
   → 要么与资源绑定，要么放 vault 由代理兑换
```
