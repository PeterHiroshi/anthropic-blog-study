## 概述

2026 年 3 月到 4 月，大量用户反馈 Claude Code "变笨了"——更健忘、更敷衍、能力下降。Anthropic 把根因追溯到**三个各自独立的变更**，影响范围覆盖 Claude Code、Claude Agent SDK 和 Claude Cowork。

与 [2025年9月那篇事后分析](../a-postmortem-of-three-recent-issues/) 最关键的区别是：**这次没有基础设施故障，也没有改动模型权重。** 三个问题分别是一个默认值、一次缓存优化、一行系统提示——全都是产品侧的决策与代码。

> "这不是用户应该从 Claude Code 得到的体验。"

**打个比方**：上一次是"发动机出了问题"（硬件、路由、编译器）；这一次是"车没坏，但有人偷偷把座椅调低了、把后视镜蒙住了、还给司机贴了张'说话不许超过25个字'的纸条"。车本身完好，开起来就是不对劲。

## 问题 1：推理强度默认值被下调

### 时间线
- **3月4日：** 默认 reasoning effort 从 `high` 改为 `medium`
- **4月7日：** 收到用户反馈后回滚

### 发生了什么

```
要解决的问题：
  高推理强度 → 延迟很长
  → 命令行界面看起来像"卡死"了
  → 用户面对一个没反应的终端

做出的改动：
  默认 reasoning effort: high ──────► medium
  受影响：Sonnet 4.6、Opus 4.6

内部评估测出的权衡：
  medium 强度 = 智能略微下降
              + 延迟显著降低
  → 内部判断这笔买卖划算
```

### 为什么这个判断是错的

**这里的关键点很反直觉：Anthropic 的评估数据是准的，错的是"值不值"的判断。**

```
Anthropic 的假设：  "用户想要快速响应。"
用户的真实偏好：    "我们要的是聪明。慢点没关系，我们等得起。"

→ 原文："users began reporting that Claude Code felt less intelligent"
   （用户开始反馈 Claude Code 感觉没那么聪明了）
```

**打个比方**：这就像餐厅老板发现"上菜快 5 分钟、味道差一点点"能让翻台率提高，于是全店改火候。数据没错——味道确实只差"一点点"。但食客来这家店本来就是冲着味道来的，不是冲着快。

这不是工程 Bug，而是**产品判断失误**：一个在内部指标上最优、但对真实用户群体错误的权衡。再多的评估覆盖率也抓不到这个问题，**因为评估本身没算错**。

### 修复方案

```
4月7日回滚：
├── Opus 4.7        → xhigh（最高档）
└── 其他所有模型     → high
```

## 问题 2：Thinking 缓存 Bug

### 时间线
- **3月26日：** prompt caching 优化上线
- **4月10日：** v2.1.101 修复

### 本来想解决什么

```
观察到的问题：
  一个会话长时间闲置（超过 1 小时）
  → 它的 prompt cache 条目过期了
  → 下一轮必须把**整个 thinking 历史**重新发一遍
  → 又贵又慢

想做的优化：
  恢复闲置会话时，把旧的 reasoning 块**清理一次**，
  只保留最近的一个。

实现手段：
  clear_thinking_20251015 API 头  +  keep:1
```

### Bug 是什么

```
【预期】行为：
  第 1 轮（闲置恢复）→ 清理旧 thinking ✓（只此一次）
  第 2 轮             → 保留 thinking
  第 3 轮             → 保留 thinking
  第 4 轮             → 保留 thinking
  → 缓存命中，历史完整

【实际】行为：
  第 1 轮 → 清理 thinking ✓
  第 2 轮 → 清理 thinking ✗  ← 不该清
  第 3 轮 → 清理 thinking ✗
  第 4 轮 → 清理 thinking ✗
  → 原文："本该只清理一次 thinking 历史，
          实际却在会话剩下的每一轮都清"
```

**打个比方**：本意是"进办公室前把昨天的草稿纸扔掉一次"，结果变成了"每写完一段就把自己刚打的草稿全扔了"。于是这个人每写一句话都要重新想一遍前因后果——既慢，又容易重复自己。

### 两头受伤

```
第一头 —— 质量
  后续每次请求都丢掉 thinking 块
  → Claude 丢失了自己跨轮次的推理链条
  → 症状：健忘
          重复（把已经推导出的结论再推一遍）
          工具选择反常

第二头 —— 成本 / 用量额度
  每轮都丢 thinking 块 → 每轮的 prompt 前缀都在变
  → 每一轮都缓存**未命中**
  → 整个 prompt 按未缓存价格重新处理
  → 用户的用量额度消耗得比正常快
```

第二头是这个 Bug 格外让人难受的原因：**用户拿到了更差的输出，同时还为此多付了额度。**

### 为什么这么难发现

```
掩盖效应：
  一个**无关的**改动——thinking 的**显示方式**变了
  → 在大多数 CLI 会话中把可见症状压了下去
  → 原文："即使在测试外部构建时我们也没抓到它"

于是：
  ├── 内部测试：症状被显示改动挡住
  ├── 外部构建测试：症状被显示改动挡住
  └── 只有汇总的用户反馈才暴露了它
```

**教训：一个 UI 改动和一个后端改动，各自都没问题，合在一起就成了盲区。** 当一个改动会遮住另一个改动的证据时，这两个改动就不再是"互不相干"的了。

**打个比方**：厨房漏水（后端 Bug），同时有人在地上铺了块吸水地毯（显示改动）。地毯不是问题，但它让漏水看不见了——直到楼下天花板开始滴水（用户反馈）。

### Code Review 工具的回溯测试

事后，Anthropic 拿自己的 Code Review 工具去测试当初那些引入 Bug 的 PR：

| 模型 | 提供了完整仓库上下文 | 找到 Bug 了吗？ |
|------|---------------------|----------------|
| Opus 4.7 | 是 | **是** |
| Opus 4.6 | 是 | 否 |

关键限定语是：**"当提供了收集完整上下文所需的代码仓库时"**。这个 Bug 是自动化审查**可以**发现的——但前提是上下文足够多、模型足够强。这直接催生了下面的第 2 项承诺。

## 问题 3：简洁度削减提示

### 时间线
- **4月16日：** 随 Opus 4.7 一同上线
- **4月20日：** 回滚

### 发生了什么

Claude Code 的系统提示中新增了一条长度约束：

> "长度限制：工具调用之间的文本保持在 25 词以内。最终回复保持在 100 词以内，除非任务需要更多细节。"

```
本意：少废话、输出更紧凑、更好读
现实：给模型自己的"工作空间"上了硬性字数预算
```

### 为什么"限制话痨"会损伤智能

```
工具调用之间的文本**不是装饰**。那是模型用来：
  ├── 陈述刚刚学到了什么
  ├── 规划下一步
  ├── 记下必须记住的约束条件
  └── 推理下一个该用哪个工具

把它压到 25 词 ──► 你压缩的是模型**外化出来的草稿纸**

把最终回复压到 100 词 ──► 解释被截断
                          注意事项被省略
                          边界情况被丢弃
```

**打个比方**：这就像要求一个数学老师"解题过程写在便利贴上，答案不超过一行"。老师还是那个老师，但草稿空间不够，中间步骤就得省，省着省着就容易出错——而且学生也看不懂了。

### 实测数据

```
内部评估结果：
  约 3% 质量下降  ── Opus 4.6
  约 3% 质量下降  ── Opus 4.7

注意：**两个**模型版本都掉了
      → 说明问题出在提示词，不在新模型
```

**为什么 3% 比听起来严重得多：** 正如 [《量化 Agent 编程评估中的基础设施噪声》](../infrastructure-noise/) 指出的，agentic 基准测试上 3 个百分点以下的差异可能和基础设施噪声无法区分。也就是说，一个在两个模型版本上**稳定可复现**掉 3% 的改动，恰恰落在评估体系"几乎看不见"的临界线上——这正是它能顺利上线的原因。

### 修复

4月20日回滚。这是三个修复中的最后一个，因此 **v2.1.116** 成为第一个"全清"的版本。

## 为什么三个都溜了过去

```
问题 1 ──► 评估是【对的】，【决策】是错的。
            "智能略降、速度大增"被准确地测了出来，
            却被错误地估了价。
            → 评估告诉不了你用户想要什么。

问题 2 ──► 评估从来没【跑到】真实行为上。
            一个显示改动把症状从所有测试路径上抹掉了，
            内部和外部构建都一样。
            → 这是可观测性失败，不是测试失败。

问题 3 ──► 上线前评估【覆盖面不够广】。
            约 3% 的降幅，小到能藏在窄评估套件里，
            又大到用户每天都能感觉到。
            → 这是覆盖率失败。

共同线索：
  每个改动单独看都说得通。
  没有一个单独看是灾难性的。
  其中两个在时间上重叠（3月26日 – 4月7日）。
  → 用户体验到的是【总和】，反馈的也是总和。
```

## 五项改进承诺

### 1. 更多内部员工使用公开版构建

```
问题：Anthropic 员工常跑内部/开发版构建
      → 他们体验不到客户实际体验的东西
措施：提高员工对**公开版** Claude Code 构建的使用比例
      → 吃自己做的那盘菜，而不是特供版
```

### 2. 改进 Code Review 工具

```
证据：Opus 4.7 + 完整仓库上下文 **找到了**缓存 Bug
      Opus 4.6 没找到
措施：改进 Code Review 工具
      ├── 供内部使用（合并前拦住这一类 Bug）
      └── 供客户部署（把这个能力交付出去）
关键前提：多仓库上下文——模型需要看到足够多的代码库，
          才能识别跨模块的连锁影响
```

### 3. 系统提示变更加强管控

```
问题：问题 3 只是一行提示词，代价却是 3%
措施：系统提示的变更现在必须经过
      ├── 明确的审查管控
      └── **逐模型的**全面评估
          （问题 3 同时影响 4.6 和 4.7——
            单模型评估本可抓到，但窄评估套件没抓到）
```

### 4. 设置 soak period（观察期）

```
之前：改动 → 上线
之后：改动 → SOAK（在有限曝光下运行一段时间）
            → 观察 → 上线
理由：问题 2 花了约 15 天才通过用户反馈浮出水面。
      观察期能在全量曝光之前暴露这类"慢性"退化。
```

### 5. 影响智能的变更采用灰度发布

```
任何可能影响智能的变更，现在都分阶段发布：
  小比例流量 → 监控 → 放量 → 监控 → 全量

为什么这一条特别有用：
  ├── 提供了干净的 A/B 对照人群
  ├── 在观察期内限制了影响半径
  └── 让"质量到底降没降"能用数据回答，
      而不是只能靠用户情绪判断
```

## 深度思考

### 对国内产品团队的启示

这篇文章最值得国内团队借鉴的，不是"他们出了 Bug"，而是**三种失败模式各不相同、需要三种不同的防御**：

1. **问题 1 是"指标对、判断错"** — 国内产品迭代常见的"数据驱动"陷阱：A/B 测试显示某指标涨了，就上线。但如果衡量的指标（延迟）和用户真正在乎的东西（智能）不是同一个，数据越准，错得越离谱。**用户反馈渠道是评估体系的必要补充，不是可选项。**

2. **问题 2 是"两个正确的改动相乘等于错误"** — 微服务/前后端分离架构下这尤其常见：前端改了展示逻辑，后端改了数据逻辑，各自的测试都过，合起来才出事。**跨团队变更需要合并后的端到端验证。**

3. **问题 3 是"提示词就是生产代码"** — 很多团队把 prompt 当配置项随手改，不走代码评审、不做回归评估。这篇文章给了一个具体价码：**一行提示词 = 3% 质量。**

### 更深层的启示

Anthropic 这次的补偿方式值得注意：**为所有订阅用户重置额度，而不是只补偿投诉过的人**。这承认了一个事实——大多数受影响的用户不会投诉，他们只会默默觉得"这产品不如以前了"然后流失。**能发声的用户是冰山一角，补偿必须按冰山的体积来做。**

另一个层面：三个问题里有两个是"为了优化某个次要指标（延迟、成本、简洁度）而牺牲主要价值（智能）"。当一个产品的核心价值是"聪明"时，任何以聪明为代价的优化都应该被默认视为高风险变更——这正是第 5 条承诺（影响智能的变更走灰度）的真正含义。
