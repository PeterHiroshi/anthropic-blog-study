## 1. 起点：两堵墙

作者同时在追两个目标——让 Claude 产出**真正好看的前端设计**，以及让它**自主构建完整应用**。提示词工程和单 Agent 的 harness 调优，都撞到了天花板。

破局灵感来自一个老概念：**GAN（生成对抗网络）**。GAN 之所以有效，是因为生成器和判别器是**两个独立网络、各有独立目标**。把这个结构搬到 Agent 上，就得到了生成器 Agent + 评估器 Agent，最终演化成用于多小时编程会话的三 Agent 架构。

> **给初学者的类比：**
> 让一个作家自己给自己的小说打分，他永远会说"这是杰作"。
> 但如果你请一位**独立编辑**来读——一个没有参与写作、对这份稿子没有感情投入的人——你才会拿到真话。
> GAN 的洞见就是这么朴素：**裁判和选手，不能是同一个人。**

## 2. 为什么朴素做法不够用

### 2.1 上下文退化

模型会随着上下文窗口被填满而**失去连贯性**。注意，这不只是"超出长度被截断"的问题——质量在远未触及上限时就开始滑坡。

文章点名了一个具体症状：**"上下文焦虑"（context anxiety）**。Claude Sonnet 4.5 在接近它**自己感知到的** token 上限时，会开始**提前草草收尾**——急着把活儿了结，而不是继续把事情做好。

| 策略 | 做了什么 | 结论 |
|------|---------|------|
| **压缩（compaction）** | 总结历史，保留连续性 | 保住了连续性，但把"退化"一起带进了新窗口 |
| **上下文重置（reset）** | 清空窗口，从结构化交接重新开始 | **更好**——一块真正干净的白板 |

> **给初学者的类比：**
> **压缩**像是把一间堆满杂物的房间整理成压缩包塞回同一间房——东西少了，但房间还是那间房，你还是站在那堆旧东西的气味里。
> **重置**像是搬进一间空房间，只带一张写着"上次做到哪儿、下一步做什么"的便签。
> 长跑选手中途需要的不是"把汗擦干净"，而是**换一双新鞋**。

### 2.2 自评偏差

让 Agent 给自己的产出打分，它会自信地夸奖平庸的作品。这在**主观任务**上最严重——尤其是设计，因为那里**没有二元验证**（没有一套跑完变红或变绿的测试）。

- ❌ 失败的思路：把生成器调教得更自我批判。
- ✅ 有效的思路：**把评估彻底移出生成器。**

```
      自我评估                            分离式评估
   ┌──────────────┐                  ┌──────────┐   ┌───────────┐
   │   生成器      │                  │  生成器   │ → │  评估器    │
   │  "做得真棒!"✓ │                  │          │ ← │ (全新上下文)│
   └──────────────┘                  └──────────┘   └───────────┘
   没有任何杠杆                        有杠杆：一个对产出
                                      毫无感情投入的批评者
```

## 3. 前端设计：把"主观质量"变成可评分的

设计的难点在于"好看"无法被自动检查。作者的解法不是去定义什么叫好看，而是把它变成**可评分的（gradable）**——写死明确的标准，交给一个独立 Agent 去执行。

### 四条评分标准

| 标准 | 衡量什么 |
|------|---------|
| **Design Quality 设计质量** | 连贯性、氛围、独特的视觉识别 |
| **Originality 原创性** | 自主的设计决策，而非退回模板默认值 |
| **Craft 工艺** | 排版、间距、配色、对比度 |
| **Functionality 功能性** | 可用性，用户能否完成任务 |

**权重上的关键洞见：** 评估器**更侧重 Design Quality 和 Originality**，因为 Claude 默认在 Craft 和 Functionality 上本来就得分不错。只有在前两项上持续施压，产出才会脱离"通用感"。

> **给初学者的类比：**
> 一个学生数学一直考 95 分、语文一直考 60 分。你还天天让他刷数学题，总分是提不上去的。
> 评估器在这里做的就是**把补习资源压在短板上**。

### 循环长什么样

```
 ┌─────────────┐   写出 HTML/CSS/JS      ┌──────────────┐
 │   生成器     │ ──────────────────────► │  真实运行页面  │
 └─────────────┘                          └──────┬───────┘
        ▲                                        │
        │                                 Playwright MCP：
        │  批评意见喂给下一轮迭代            导航、点击、
        │                                  截图、检查
        │                                        │
        │            ┌──────────────┐            │
        └─────────── │    评估器     │ ◄──────────┘
                     │  按 4 条标准  │
                     │    打分       │
                     └──────────────┘

 基于 Claude Agent SDK + Playwright MCP 搭建
 单次运行 4 小时以上，每次生成迭代 5–15 轮
```

关键在于：评估器**不是**看源码打分，也不是看一张静态截图打分——它先**真实操作运行中的页面**，然后才评分。

### 博物馆网站的例子

一个荷兰艺术博物馆网站，最初是一个**常规的深色主题落地页**，前九轮都在做渐进式的打磨。然后在**第十轮迭代**，生成器**彻底推翻了原方案**，把网站重新构想成一个**空间体验**：用 CSS 透视渲染出的 3D 房间与棋盘格地板，画作以自由位置挂在墙上，通过门洞在各个展厅之间导航。

> **这正是给"原创性"打分的回报。**
> 如果只考核工艺，你会得到一个越来越精致的深色落地页。
> 持续施加原创性的压力，最终逼出的是一次**质变**，而不是又一轮抛光。

## 4. 扩展到全栈：三 Agent 架构

```
┌──────────────────────────────────────────────────────────────┐
│  PLANNER 规划器                                               │
│  简短提示 ──► 详细产品规格                                     │
│  • 强调有野心的「范围」和高层技术方向                           │
│  • 刻意「不」过度指定实现细节                                   │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
        ┌──────── 协商 sprint 契约 ────────────┐
        │  生成器 + 评估器在「实现之前」        │
        │  就交付物和成功标准达成一致           │
        └───────────────────┬──────────────────┘
                            ▼
┌──────────────────────────┐        ┌──────────────────────────┐
│  GENERATOR 生成器         │───────►│  EVALUATOR 评估器         │
│  实现当前 sprint          │        │  像「用户」一样用          │
│  React · Vite · FastAPI  │◄───────│  Playwright 测试          │
│  SQLite/PostgreSQL · git │  QA    │  检查 UI + API + 数据库    │
│  交付 QA 前先自检         │        │  有硬性阈值                │
└──────────────────────────┘        └──────────────────────────┘
```

### 各组件职责

| Agent | 职责 | 关键设计选择 |
|-------|------|-------------|
| **Planner 规划器** | 把一句话简报扩展成完整产品规格 | 范围要有野心 + 给出技术方向，但让实现细节**自然涌现** |
| **Generator 生成器** | 逐个功能、分 sprint 构建 | 真实技术栈（React/Vite/FastAPI/SQLite 或 PostgreSQL）+ git 版本控制 |
| **Evaluator 评估器** | 对照具体标准做验证 | 像用户一样点击应用；按产品深度、功能性、设计、代码质量打分，带硬性阈值 |

### Sprint 契约

每个 sprint 开始**之前**，生成器和评估器要**协商一份契约**——本轮交付什么、什么算成功——然后才开始写代码。

> **给初学者的类比：**
> 这就是"先签验收标准，再开工"。
> 没有契约的工程队，干完之后总有办法论证"我交付的就是我该交付的"。
> 先把验收单贴在墙上，事后就没得狡辩了。

## 5. 实证对比：单 Agent vs 完整 Harness

同一个提示词（一个 **2D 复古游戏制作器**），同一个模型（**Claude Opus 4.5**）：

| | 单 Agent 直跑 | 完整 Harness |
|---|-------------|-------------|
| **耗时** | 20 分钟 | 6 小时 |
| **成本** | $9 | $200 |
| **结果** | **核心功能是坏的** —— 实体能显示出来，但不响应输入 | **完整可玩的游戏** |
| **功能** | — | 精灵动画系统、行为模板、AI 辅助生成、游戏导出 |

规划器把那一句话的提示词扩展成了**跨十个 sprint 的 16 个功能**。

> **必须诚实地看这组数字：** 成本约 22 倍，时间约 18 倍。
> 这不是免费的午餐，而是一次**刻意的交换**——在"质量才是瓶颈"的任务上，用算力换质量。
> 反过来说：如果你的任务 20 分钟就能做对，那就别上 harness。

## 6. 迭代：模型变强，就该删掉复杂度

**Claude Opus 4.6** 发布后——它规划得更审慎、能把 Agent 任务维持得更久、代码审查和调试能力更强——作者做了一件反直觉的事：**把 harness 删掉了一部分。**

```
    OPUS 4.5 时期的 HARNESS              OPUS 4.6 时期的 HARNESS
    ┌─────────┐                          ┌─────────┐
    │ 规划器   │                          │ 规划器   │
    └────┬────┘                          └────┬────┘
         ▼                                    ▼
    ┌─────────────┐                      ┌───────────┐
    │  SPRINT     │  ◄── 被移除           │  生成器    │ （一次长连贯运行）
    │  拆分机制    │                      └─────┬─────┘
    └────┬────────┘                            ▼
         ▼                                 ┌───────────┐
    ┌───────────┐                          │  评估器    │
    │  评估器    │                          └───────────┘
    └───────────┘
```

**Sprint 机制被移除**，规划器和评估器保留。评估器转向"运行结束后单次打分"——但在**逼近模型能力边界**的任务上，它依然有价值。

### 成果：浏览器里的 DAW

用更新后的 harness 构建一个 **DAW（数字音频工作站）**：

| 指标 | 数值 |
|------|------|
| 总耗时 | 约 3 小时 50 分钟 |
| 总成本 | **$124.70** |

而且关键在于——**评估器依然证明了自己的价值**。它抓到了生成器遗漏、却已经上报为"完成"的真实缺口，包括**缺失的交互功能**和**并未真正实现的音频录制功能**。

> **注意数字的方向：** harness 更简单了，任务野心相当，成本反而**更低**（约 $125 vs 约 $200）。
> 那些复杂度，本来是替 4.5 扛着的；4.6 自己扛得住了。

## 7. 核心结论

> **模型能力越强，harness 复杂度应当越低。**

Harness 的**每一个组件，都编码着一条关于"模型有什么缺陷"的假设**。Sprint 机制编码的是"这个模型撑不住一次长时间的连贯构建"；压缩机制编码的是"这个模型管不好自己的上下文"。而这些假设，**都是有保质期的**。

```
        模型能力 ──────────────────────────►
        │
        │  ████████████  harness 复杂度
        │  ████████
        │  ████
        │
        │  ░░░░  模型独立能力
        │  ░░░░░░░░
        │  ░░░░░░░░░░░░
        ▼
   「独立能力的边界」在向外推移。
   Harness 的工作是被「重定向」，而不是被「消灭」。
```

> **给初学者的类比：**
> Harness 就像**学游泳时的浮板**。
> 浮板的存在，本身就是在说"这个人还不会踩水"。
> 学员进步了，你不把浮板拿掉，浮板反而变成了阻力。
> 但——教练并不会因此失业，**他只是改教转身和呼吸节奏了。**

### 操作原则

```
1. 先找最简单的方案，只在确有必要时才增加复杂度。

2. 每个 harness 组件都编码了一条「模型缺陷」假设
   —— 定期对这些假设做压力测试。

3. 每次模型发新版本，都把你的 harness 重跑一遍。

4. 在「真实问题」上读 trace —— 不要抽象地空想模型的局限。

5. 删掉那些不再承重的组件。
```

作者明确表示这**不是**在论证"harness 设计会消失"：随着模型变强，有趣的 harness 组合空间并不会缩小——**它只是移动了位置。**

## 8. 附录：RetroForge 规划器输出

文章附上了一份规划器输出的实例——由那句"2D 复古游戏制作器"提示词生成的完整规格，命名为 **RetroForge**。它的结构展示了"扩展"到底意味着什么：

- **Overview 概览** —— 平台定位与目标用户
- **Features 功能**，拆成若干子章节，例如：
  - **Project Dashboard & Management 项目面板与管理** —— 用户故事涵盖新建、以视觉卡片形式浏览、打开编辑、带确认的删除、复制
  - **Project Data Model 项目数据模型** —— 元数据结构，包括分辨率、瓦片尺寸、调色板与内容
  - 后续章节涵盖基于瓦片的关卡编辑、像素画精灵制作、可视化实体行为系统、可试玩测试模式

附录的意义在于把"把简短提示扩展成详细规格"这句话变得**具体可感**——并且展示了规划器写的是**用户故事和数据模型，而不是代码**。

## 核心要点速查

```
1. 把评估器从生成器里分离出来
   → Agent 无法给自己打分，「拆开」本身就是杠杆

2. 重置优于压缩
   → 压缩保连续性，重置给干净白板
   → 警惕「上下文焦虑」：接近 token 上限时草草收尾

3. 把主观质量变成可评分的
   → 设计质量 · 原创性 · 工艺 · 功能性
   → 权重压在模型「弱」的那两项（质量、原创性）上

4. 评估「运行中的产物」，而不是代码
   → Playwright：点 UI、打 API、查数据库状态

5. 先签契约，再开工
   → 实现之前就定好成功标准，而不是事后追认

6. Harness 要么挣回它的成本，要么就不该存在
   → 20分钟/$9 是坏的 vs 6小时/$200 是可玩的（Opus 4.5 游戏制作器）

7. 模型变强，复杂度就该缩小
   → Opus 4.6 → 移除 sprint，保留规划器 + 评估器
   → DAW：约 3小时50分，$124.70 —— 评估器依然抓到了真实缺口

8. 先找最简单的方案
   → 只在确有必要时才增加复杂度
   → 更强的模型「重定向」harness 工作，而不是消灭它
```
